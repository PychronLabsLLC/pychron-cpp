## 1. Goals, non-goals, principles

### 1.1 Goals

1. One shared, network-reachable PostgreSQL database per lab is the single
   source of truth for catalog, values, revisions, reference data and raw
   signals (ADR-0002 section 2, Amendment A).
2. Acquisition never blocks or fails a run because of the network, the
   server, or git. A save is one local SQLite transaction (Amendment B).
3. Reduction and visualization clients on other desktops are concurrent
   writers with optimistic concurrency and a full audit trail.
4. Every value that today lives in a per-analysis JSON file is queryable in
   SQL. The `CurrentTbl` shadow table has no successor
   (`dvc_persister.py:667-707`, `dvc.py:1916-2047`).
5. The importer and publisher round-trip the existing repo layout: import a
   real project, publish it, and the files for unchanged analyses are
   byte-identical (ADR-0002 action items 3 and 4).

### 1.2 Non-goals

- Two-way git sync. Git is a one-way mirror; hand edits re-enter as imports
  with a conflict report (ADR-0002 section 4.3).
- SQLite as a shared lab database, in any configuration (Amendment C).
- An application server. Clients talk to PostgreSQL directly through one
  C++ access layer. The only server-side code is constraints and triggers.
- Reproducing MySQL/MSSQL quirks (`dvc_database.py:747-756`).

### 1.3 Principles

| # | Principle | Consequence in the schema |
|---|---|---|
| P1 | Immutable revisions first | Revision and payload rows are insert-only, enforced by triggers. Only `head`, `derived_value` (a cache) and operational tables (outbox, leases, publish state) are mutable. |
| P2 | The analysis row is immutable after ingest | Comments, tags, identity fixes and every reduction choice are revisions. The analysis row's denormalized identity columns change only through an `identity` revision (section 5.6). |
| P3 | Client-generated ids | All primary keys are UUIDv7 (RFC 9562) generated by the writer. Server sequences are used only for the change cursor (section 9). Imported legacy analyses keep their legacy UUIDs. |
| P4 | UTC everywhere | `timestamptz` in PostgreSQL, ISO-8601 text with a `Z` suffix in SQLite (CHECK enforced). Legacy naive local timestamps are converted at import with the lab's configured IANA zone and converted back by the publisher (section 10.4). |
| P5 | No git on hot paths | Nothing in acquisition, reduction or browsing calls git. Only the publisher and importer do. |
| P6 | One schema, one access layer | Same DDL on both engines (dialect notes in section 11.3). No SQL text outside `libs/persistence/src/sql/`. |
| P7 | Content addressing for immutable bytes | Signal blobs, spectrometer snapshots and script texts are keyed by SHA-256 of their canonical bytes, so uploads are idempotent. |
| P8 | Unknown fields survive | Payload tables carry an `extra` JSON column holding keys the schema does not model, so the importer never drops data and the publisher can reproduce the file. |

## 2. Topology

```
            lab network (TLS)                                      off-site
 +--------------------------------+                         +-------------------+
 |  PostgreSQL "pychron" database |  <-- publisher (bg) --> |  git hosts        |
 |  catalog, values, revisions,   |       one-way mirror    |  (GitHub, Gitea)  |
 |  reference data, signal blobs, |                         +-------------------+
 |  change_log, leases            |  <-- importer (admin) -- existing repos
 +--------------------------------+
     ^  ^ LISTEN/NOTIFY + cursor          ^
     |  |                                  |
     |  +---------------+                  |
     |                  |                  |
 +---+--------------+  +-+--------------+  +-----------------+
 | acquisition PC   |  | reduction PC   |  | viewer PC       |
 |  executor        |  |  writer (CAS)  |  |  read-only      |
 |  outbox.sqlite   |  +----------------+  +-----------------+
 |  (WAL, durable)  |
 |  uploader (bg) --+--> idempotent ingest
 +------------------+
```

- The server may run on a lab server or, in a one-spectrometer lab, on the
  acquisition PC itself. The topology is the same in both cases. Clients on
  other desktops connect to it over the network, and the acquisition
  executor still writes to its outbox first.
- The engine choice follows how many machines touch the data, not how many
  instruments the lab has. Any lab whose data is read on a second desktop
  needs the server, and so every lab does.
- SQLite appears only as (a) the acquisition outbox/spool, (b) the
  portable offline export, and (c) the test engine.

### 3.8 What acquisition may create

At ingest, acquisition may create only: `analysis` and its satellite rows,
`measured_position`, `load` (ensure-by-name, as `dvc_persister.py:623-632`
does today), `app_user` (ensure-by-name), `experiment_queue`,
`spectrometer_snapshot`, `script_text`, `signal_blob`, and its own
collection changeset. Outbox payloads refer to catalog rows by **natural
key** (identifier text, load name, user name, spectrometer name). The ingest
transaction resolves them to UUIDs, so an acquisition PC never needs a
server-issued id.

deferred to a lab-management spec. Catalog migration from the legacy MySQL
database copies them verbatim into a read-only `legacy` schema so nothing is
lost.

### 4.2 Raw data references

Raw arrays are never stored in payload rows. `signal_ref.blob_sha`,
`peak_center.points_blob_sha`, `monitor_check.data_blob_sha` and
`analysis_artifact.blob_sha` all reference `signal_blob` (section 7).

### 4.3 Derived values (cache, not record)

The experiment spec (section 8.3) keeps derived values out of the
`AnalysisRecord`. ADR-0002 section 4.1 wants derived ages queryable. Both
hold if derived values are a **cache**:

`derived_value` (PK `analysis_uuid`,`fingerprint`,`name`): `value`,
`error`, `units`, `reduction_version`, `computed_utc`.
`fingerprint = SHA-256(head revision uuids of all kinds, resolved reference
revision uuids, reduction_version)`.

A cached row is valid only while its fingerprint equals the analysis's
current inputs. Any client may recompute and insert. Stale rows are garbage
and may be deleted. This is the only value table that allows DELETE. It
replaces `CurrentTbl` and `_update_current*` (`dvc.py:1916-2047`).
Interpreted ages are user decisions, not cache entries (section 5.7).

## 5. Revision model

### 5.1 Entities

```
changeset 1---* revision *---1 subject (analysis | ref_object | interpreted_age)
    |               | parent (same subject, same kind; nullable for roots)
    |               +--- payload rows (section 4.1 / 6.2 / 5.7)
    +---* head_move  (every pointer move, including rollbacks)
head (subject, kind) -> revision        <- the only mutable pointer
```

Columns are in Appendix A. A `changeset` (author user, client, message,
client-clock `created_utc`) is the unit of audit, like a git commit. A
`revision` names exactly one subject through one of three typed FKs
(`analysis_uuid`, `ref_object_uuid`, `ia_uuid`), CHECKed equal to
`subject_uuid`. The composite FK `head(revision_uuid, subject_uuid, kind) → revision(uuid,
subject_uuid, kind)` guarantees a head points at a revision of its own
subject and kind. `revision.parent_uuid` has the same composite constraint.

### 5.2 Kinds

| Subject | Kinds | Legacy commit tag (`dvc/__init__.py:44-54`) |
|---|---|---|
| analysis | `signals` | `COLLECTION`, `DEFINE EQUIL` |
| analysis | `intercepts`, `baselines` | `ISOEVO` |
| analysis | `blanks` | `BLANKS` |
| analysis | `icfactors` | `ICFactor` |
| analysis | `tags` | `TAG` |
| analysis | `annotation`, `identity`, `cosmogenic` | `MANUAL`, (none), (none) |
| analysis | `refpins` | `FLUX_FREEZE`, `PR_FREEZE` (`dvc.py:704`, `:729`) |
| interpreted_age | `interpreted_age` | `IA` (`dvc.py:1612`) |
| ref_object | `value` | meta repo commits |

There is one head per (analysis, kind), not one per analysis. Legacy history
is per file (`.intercepts`, `.blanks`, ...). Different clients edit
different kinds (one person fits blanks while another sets IC factors), so
per-kind heads make those edits independent instead of conflicting. A
"fits" save that touches intercepts and baselines (`dvc_analysis.py:462`)
is one changeset with two revisions.

### 5.3 Collection changeset

At ingest the server creates one `collection` changeset per analysis. Its
author is the analyst and its client is the acquisition client. It holds
root revisions (parent NULL) for `signals`, `intercepts`, `baselines`,
`blanks` ("preceding", `dvc_persister.py:782-789`), `icfactors` ("default",
`:757-762`) and `tags`, and inserts their heads. The acquisition client
generates every UUID involved (changeset, revisions) and puts them in the
outbox payload, which makes the ingest idempotent (section 8).

Legacy writes four commits per save (`dvc_persister.py:363-407`). Here there
is one changeset. The publisher may still emit the four legacy messages if
byte-comparable history is wanted (section 10.4).

### 5.4 Writes and CAS

A reduction client stages revisions and head moves in a unit of work, then
commits in one transaction:

1. Insert `changeset`, `revision` rows and payload rows.
2. For each (subject, kind), in ascending (`subject_uuid`,`kind`) order to
   avoid deadlocks, run:
   `UPDATE head SET revision_uuid=:new, head_version=head_version+1
    WHERE subject_uuid=:s AND kind=:k AND revision_uuid=:expected`.
   For a first head (no expected), `INSERT ... ON CONFLICT DO NOTHING`.
3. If any statement affects 0 rows, roll back the whole transaction and
   return `Conflict` entries. Otherwise insert `head_move` rows, take the
   change cursor (section 9) and commit.

The isolation level is READ COMMITTED. The conditional UPDATE is the
compare-and-swap, so SERIALIZABLE is not needed. A changeset is
all-or-nothing: a blank fit applied to 200 analyses either lands entirely
or not at all.

**The losing writer** gets `CommitOutcome = Conflicts{[subject, kind,
expected, actual, actual_changeset{author, client, created_utc,
message}]}`. Nothing of its changeset persists. The reduction UI shows a
non-modal banner: "Blanks for 12 of these analyses were changed by
J. Smith (reduction-2) at 14:02: [Reload] [Re-apply mine]". Re-apply
re-runs the user's operation against the new heads, so the new parent is
the winner's revision. There is no silent last-writer-wins path in the
access layer.

Acquisition never contends. It only creates the root heads of its own new
analysis, and duplicates are absorbed by idempotent ingest.

### 5.5 Rollback, bookmarks, rollback-to-collection

- **Rollback** is a `rollback` changeset with no new revisions and only CAS
  head moves to an earlier revision of the same subject and kind. It is
  audited like any other change. It replaces `git checkout <sha> -- path`
  (`dvc.py:731-745`).
- **Rollback to collection** moves each kind's head to its root revision
  (the one in the analysis's `collection` changeset). Collection is an
  implicit bookmark and needs no rows.
- **Bookmarks** (`dvc.py:799-808`, git tags today):
  `bookmark(uuid, name, repository_uuid | group_uuid, message,
  author_user_uuid, created_utc)` plus `bookmark_entry(bookmark_uuid,
  subject_uuid, kind, revision_uuid)`, which captures the heads of every
  analysis in scope. Restoring a bookmark is a `bookmark_restore` changeset
  of CAS moves. The publisher mirrors a bookmark as a git tag on the commit
  that first published that state.

### 5.6 Identity revisions

`identity` revisions record (identifier, aliquot, increment) changes made by
an admin repair or by provisional renumbering (section 8.5). The same
transaction updates the denormalized `analysis` identity columns, so the
UNIQUE constraint keeps holding. Apart from `signals_state` (section 7.3),
this is the only UPDATE permitted on `analysis`, and only the admin role and
the ingest path may perform it.

### 5.7 Interpreted ages

`interpreted_age(uuid, name, identifier_uuid, repository_uuid)` has
`interpreted_age` revisions. The payload is `ia_value(revision_uuid, age,
age_err, age_kind, kca, kca_err, mswd, nanalyses, doc json)`, where `doc`
holds the full legacy dict (`dvc/func.py:171-230`), plus
`ia_member(revision_uuid, analysis_uuid, record_id, plateau_step, tag)`.
Legacy wrote a new numbered file per save (`dvc.py:2096-2115`). Here a
re-save is a new revision of the same IA.

### 6.2 Semantics

- **Head** is "what a new reduction uses", for every reference type,
  gains and sensitivity included. This keeps legacy "latest" behavior
  (`meta_repo.py:744-754` takes `spec[-1]`), so import round-trips give
  identical ages. Gains actually used during a run are immutable in the
  run's `spectrometer_snapshot` regardless.
- **Who may edit.** Any authenticated writer (acquisition or reduction role)
  may publish a new reference revision of any type. There is no separate
  lab-manager role and no approval step (decision D4). Each edit is still a
  `reference` changeset with author, client, message and CAS on the ref
  head, so it is revisioned, audited and reversible by rollback. This
  removes the meta-repo write hotspot (`dvc_persister.py:425-458`).
- **Pinning.** By default reductions resolve references at head. An
  analysis is pinned when its `refpins` head lists (`ref_object`,
  `ref_revision`) pairs, and reductions must then use the pinned revision.
  This generalizes legacy "freeze flux" and "freeze productions"
  (`dvc.py:666-729`, consumed at `dvc.py:2237-2285` via
  `analysis_loading.py:102-140`). Unfreezing is a rollback of `refpins`.
  Every `derived_value` fingerprint includes the resolved reference
  revisions, so a cached age always states which flux it used.
- **Pins still record what was used.** Because "latest" changes over
  time, the resolved reference revisions are part of every
  `derived_value` fingerprint, and an explicit freeze writes a `refpins`
  revision. An age can always be traced to the exact sensitivity, gains,
  flux and production revisions it used.

## 7. Raw signal store

### 7.1 Decision: blobs in PostgreSQL (`bytea`), content-addressed

`signal_blob(sha256 bytea(32) PK, codec text, byte_len int, n_points int,
bytes bytea, created_utc)`.

| Option | For | Against |
|---|---|---|
| **A. `bytea` rows in PostgreSQL (chosen)** | Every client already holds an authenticated TLS connection, so there is no second share, credential or mount to manage on macOS and Windows. Transactional with `signals_state`. One backup (section 12.6). `INSERT ... ON CONFLICT DO NOTHING` is idempotent. | Database size and dump/restore time grow with raw data. |
| B. Large objects (`lo`) | Streaming access for very large values | Separate ACLs, orphan cleanup (`vacuumlo`), awkward dumps. Values are far below the 1 GB `bytea` limit. |
| C. Shared content-addressed object/file store (S3/MinIO or SMB share) | Keeps the DB small; cheap storage | A second system every client must reach and authenticate to. No transactional link to rows. Windows/macOS share paths differ. |

Sizing basis: a typical multicollector analysis has about 5-10 series of
200-1000 float32 (t, v) pairs for signal, baseline and sniff, roughly 20-150
KB. At 30-80 analyses per day that is under 15 MB per day per instrument,
or about 5 GB per year. PostgreSQL handles this comfortably. These are
estimates and must be measured during the D2 stage (section 12.5).

**Trigger to revisit (any one):** `signal_blob` exceeds 60% of database
bytes and the database exceeds 250 GB; a full logical restore exceeds 4 h;
any single blob exceeds 64 MB. Migrating then means adding a `storage`
column (`db`/`object`) and moving bytes. Hashes, references and the outbox
do not change, because the store is addressed only by `sha256`.

### 7.2 Canonical encoding and hash

- Codec `f32le-tv/1`: little-endian float32 interleaved (t, v). Codec
  `f32le-tvs/1` adds sigma (`AnalysisRecord` `Trace`). Peak-center points
  and monitor data use `f32le-tv/1`.
- `sha256 = SHA-256(codec_id || 0x00 || bytes)`. The server recomputes it
  on insert (`sha256()` is built into PostgreSQL 11+) and rejects a
  mismatch.
- Legacy `.data.json` stores base64 of big-endian `>ff` pairs
  (`dvc_persister.py:902`, `processing/isotope.py:108-116`). Float32 values
  convert exactly in both directions, so the importer re-encodes to
  `f32le-tv/1` and the publisher re-encodes to `>ff` base64 with identical
  bytes.

### 7.3 Availability

Uploads go catalog, then analysis, then blobs (section 8.3). An analysis can
therefore exist briefly with `signals_state = 'pending'`. Each blob ingest
transaction checks whether every `signal_ref`/`peak_center`/`monitor_check`
blob of that analysis is now present. If so it sets `complete` and emits a
change. Viewers show "signals uploading" for pending analyses. Values
(intercepts and so on) are usable immediately. `signal_ref.blob_sha` has no
FK to `signal_blob` for this reason. Invariant I13 covers it instead.

## 8. Coordination and the acquisition outbox

### 8.1 Save path

`SavePhase` → `OutboxPersister::save_analysis(record)` runs one SQLite
transaction in `outbox.sqlite` (`journal_mode=WAL`, `synchronous=FULL`):

1. Generate UUIDv7s for the collection changeset and its revisions. The
   analysis UUID already exists from `begin_run`.
2. `INSERT OR IGNORE` each raw series into `outbox_blob` (keyed by sha256).
3. Insert `outbox_item` rows: `catalog` (load/user ensure, if any), then
   `analysis` (canonical payload: `AnalysisRecord` plus the generated ids),
   then one `blob` item per distinct sha. Dependencies go in `outbox_dep`.
4. Commit. The run is saved. `SavePhase` returns.

This is the experiment spec's spool (section 8.4 there). The outbox *is*
the spool, and the uploader is "the configured persister on the
Scheduler". `FilePersister` remains an optional export sink.

### 8.2 Outbox schema (SQLite only)

| Table | Columns |
|---|---|
| `outbox_item` | `seq` INTEGER PK AUTOINCREMENT, `item_uuid` TEXT UNIQUE (idempotency key), `kind` (`catalog`/`queue`/`analysis`/`blob`/`lease_release`/`changeset`), `analysis_uuid`, `payload` BLOB, `payload_sha256`, `payload_schema_version`, `created_utc`, `state` (`pending`/`in_flight`/`done`/`poison`/`conflict`), `attempts`, `next_attempt_utc`, `last_attempt_utc`, `last_error_class` (`retryable`/`permanent`/`conflict`), `last_error`, `server_change_seq`, `acked_utc` |
| `outbox_dep` | `item_uuid`, `depends_on_uuid` (PK both) |
| `outbox_blob` | `sha256` PK, `codec`, `bytes`, `created_utc` |
| `lease_cache` | `identifier`, `aliquot`, `lease_uuid`, `state` (`leased`/`used`/`released`), `expires_utc`, PK(`identifier`,`aliquot`) |
| `local_allocation` | `identifier`, `aliquot`, `increment`, `analysis_uuid`, `provisional`, PK(`identifier`,`aliquot`,`increment`) |
| `catalog_cache` | `entity_type`, `natural_key`, `uuid`, `doc` (json), `change_seq`. Read-only mirror for offline queue building (acquisition only). |
| `outbox_meta` | `key` PK, `value`: `client_uuid`, `server_db_id`, `server_cursor`, `schema_version` |

**Idempotency keys.** For an `analysis` item, `item_uuid` = the analysis
UUID. For a `blob` item it is UUIDv5(pychron namespace, sha256), so a blob
shared by two analyses is spooled once (`INSERT OR IGNORE`). For others it
is a UUIDv7 generated at spool time. The payload carries every server row
id (changeset, revisions). Re-sending an item therefore cannot create a
second copy of anything. Blob ingest needs no receipt: the insert is
`ON CONFLICT DO NOTHING` on the content hash.

### 8.3 Uploader

A single background task on the Scheduler. It is the only writer that moves
outbox state. It runs a loop:

1. Pick the lowest `seq` item with `state = pending`,
   `next_attempt_utc <= now`, and all dependencies `done`. Mark it
   `in_flight`. An `in_flight` item found at startup is reset to `pending`.
2. Run one server transaction for the item:
   - Look up `ingest_receipt(item_uuid)`. If it exists with the same
     `payload_sha256`, this is a duplicate: return the stored ack. If it
     exists with a different sha, the result is permanent error
     `IdempotencyMismatch`.
   - Otherwise apply the item, then insert `ingest_receipt`, take the change
     cursor and commit.
3. On success, set `done`, `server_change_seq` and `acked_utc`.
4. On a retryable failure (connection refused or lost, timeout,
   `40001`/`40P01` serialization or deadlock, `57P01` admin shutdown,
   `53xxx` resources): `attempts++`, `next_attempt_utc = now + min(300 s,
   2 s * 2^attempts) * jitter(0.5..1.5)`, back to `pending`. There is no
   attempt limit.
5. On a permanent failure (constraint or validation error, unknown natural
   key, idempotency mismatch, unsupported payload version): retry twice
   more at the normal backoff to rule out misclassification, then set
   `poison`. Dependents stay `pending`, blocked. **Other analyses keep
   flowing.** There is no head-of-line blocking across dependency chains.

Ordering is catalog before analyses before blobs, enforced by
`outbox_dep`, not by `seq`. Across independent analyses, order is `seq`
(spool order). A shared blob item depends on the first analysis that
spooled it. A later analysis whose blobs are all already on the server is
ingested directly as `signals_state = 'complete'`.

Retention: `done` payloads and blobs stay locally for 30 days (configurable),
then `VACUUM`-compacted. `poison` items are kept until resolved.

### 8.4 What the operator sees

Status only, never a prompt (replacing `dvc_persister.py:423`, `:454`). The
executor pane's pending-persist counter (experiment spec 10.4) shows
`Upload: synced | 3 pending (oldest 4 min) | offline since 13:10 |
attention: 1 poison`. Non-modal alarms through the existing AlarmDock fire
when the server has been unreachable for 30 minutes, when any item is
poison, or when outbox free disk drops below threshold. The queue never
pauses for upload state.

The single local precondition a run checks (an `IPreRunCheck`) is that the
outbox volume has at least N GB free (default 5) and is writable. Server
reachability is never a pre-run check.

Admin commands: `elctl persist status | retry <item|all-poison> |
show <item> | export <item> <file>`. Poison is resolved by fixing the cause
server-side (for example, creating a missing identifier) and then
`retry`.

### 8.5 Aliquot and step allocation

The legacy rule is `max(aliquot) + 1` from the database at run time
(`dvc_database.py:1376-1398`, `:1400-1419`, `experiment/datahub.py:137-181`),
with no lock and no UNIQUE constraint. That requires a live server, and two
instruments can race.

**Decision: advance reservation (leases), with a narrow provisional
fallback.** Local allocation in a per-instrument namespace followed by
reconciliation was rejected. Run IDs (`66573-07A`) are human identifiers
that appear in notebooks, filenames, plots and publications within minutes
of a run. Renumbering as the normal reconciliation path would make them
unstable. Leases make the common case conflict-free and offline-safe, and
limit renumbering to a rare, flagged case.

Server table `aliquot_lease(identifier_uuid, aliquot, client_uuid,
queue_uuid, state, leased_utc, expires_utc)`, PK(`identifier_uuid`,
`aliquot`).

- **Reserve.** In one transaction, lock the identifier row (`SELECT ... FOR
  UPDATE` on `identifier`; `BEGIN IMMEDIATE` on SQLite), compute `next =
  1 + max(max analysis aliquot, max leased aliquot)`, and insert k lease
  rows.
- **Unknown identifiers.** When a queue is started, or edited while online,
  the executor reserves one aliquot per non-step-heat run, and one per
  step-heat aliquot, for every identifier in the queue. It adds headroom of
  2 per identifier for inserted runs. Leases expire after 14 days unused.
- **Special identifiers** (`bu-FD-J`, `a-FD-J`, ...) embed the
  spectrometer code and are only ever run by that instrument. The
  instrument holds a standing block of 200, renewed by the uploader when 75%
  of it is used. In practice it never runs out during an outage.
- **Steps.** Whoever holds the aliquot lease owns that aliquot's steps and
  allocates them locally in `local_allocation`. No server round trip.
- **Release.** At queue end, unused leases go to `lease_release` outbox
  items. Released aliquots below the identifier's high-water mark become
  gaps. Gaps are allowed, as with cancelled runs today (decision D2).
- **Offline, no lease** (an unknown identifier added to a queue during an
  outage, or one whose leases ran out): the run **still runs**. It gets a
  provisional aliquot `max(server high-water in catalog_cache,
  local max) + 1`, `provisional = true`. The UI shows it as `66573-12A*`.
  At ingest the server checks it. If (identifier, aliquot) is free, it
  converts the allocation into a `used` lease and clears `provisional`.
  Otherwise it assigns the next free aliquot, writes an `identity`
  revision (`reason = provisional_renumber`), records a `sync_conflict`
  row, and the acquisition client updates its local display.

Consequences (accepted, decision D1): a queue started online never
renumbers. Only runs added while offline can, and they are visibly marked
until confirmed. A renumber is a `sync_conflict` row of kind
`provisional_renumber` (section 8.7), visible to the operator and admins. Unique
(identifier, aliquot, increment) is enforced by the server either way.
Ingest of a non-provisional analysis requires a lease held by its client or
an existing `used` lease (invariant I10).

### 8.6 Identifier reservation (labnumbers)

New unknown identifiers are assigned during irradiation entry, never during
acquisition. Today this is `get_greatest_identifier` plus one
(`dvc_database.py:1234-1239`), unlocked. The replacement is
`identifier_counter` updated with `UPDATE ... SET last_value = last_value
+ :n RETURNING last_value` in the same transaction that inserts the
`identifier` rows. Entry tools require the server. Offline labnumber
assignment is not supported, which is not a regression.

### 8.7 Offline export edits (decision D3)

The offline export (D7) is a SQLite file holding the exported subset of the
shared schema, the outbox tables, and `outbox_meta.server_cursor` (the
`change_seq` it reflects). It is writable. Edits made in it go through the
same `IStore`/unit-of-work code as online edits:

1. **Record locally.** A reduction edit, rollback, bookmark restore,
   reference edit, interpreted age or group edit commits a normal
   changeset into the export's own tables, with CAS against the export's
   local heads. Ids are client-generated UUIDv7, so they stay valid on the
   server. The same SQLite transaction spools one `outbox_item` of kind
   `changeset` whose payload is the changeset, its revisions and payload
   rows, and its head moves, each move with its **expected head** as it
   was in the export. A later offline changeset that builds on an earlier
   un-uploaded one gets an `outbox_dep` on it.
2. **Not allowed offline:** ingesting analyses, catalog edits (D6: catalog
   rows have no CAS anchor), lease or identifier allocation. These are
   rejected locally with `Config` ("requires server").
3. **Upload.** When the server is reachable, the uploader applies each
   `changeset` item as one server transaction with the section 5.4 CAS
   rules. `ingest_receipt` makes a retry after a lost ack idempotent.
4. **Conflict.** If any expected head differs on the server, the server
   transaction rolls back. The server records a `sync_conflict` row
   (changeset, client, user, each subject/kind with expected and actual
   heads, the winning changeset). The local item moves to state
   `conflict`, which is not `poison` and is not retried automatically.
   Dependent items move to `conflict` as well. The export UI lists
   conflicts with the winner's author and message, and offers **Refresh
   and re-apply** (pull server changes since `server_cursor`, then re-run
   the user's operation against the new heads as a new changeset with a new
   `item_uuid`) or **Discard** (drop the local changeset and refresh).
   Resolution is written back to `sync_conflict.resolution`.
5. **Refresh.** Pulling server changes into the export is a read sync by
   change cursor (section 9.2). Local heads that were never uploaded are
   rebased only by re-apply, never by merging rows.

The acquisition PC's outbox uses the same `sync_conflict` table for
provisional renumbering (section 8.5).

## 9. Change cursor and notifications

### 9.1 Cursor

`change_counter(id = 1, seq bigint)` holds a single row. `change_log` has
`change_seq` PK, `committed_utc` (server `now()`), `changeset_uuid`,
`client_uuid`, `kind` (`changeset`/`ingest`/`blob_complete`/`catalog`/`lease`).
`change_entity` has `change_seq`, `entity_type`, `entity_uuid`, PK all
three, IX(`entity_type`,`entity_uuid`).

Every writing transaction, as its **last** statements before COMMIT, runs:

```sql
UPDATE change_counter SET seq = seq + 1 WHERE id = 1 RETURNING seq;   -- row lock
INSERT INTO change_log (...) VALUES (:seq, ...);
INSERT INTO change_entity (...) VALUES ...;
SELECT pg_notify('pychron_change', :payload);                          -- PG only
COMMIT;
```

Why not `bigserial`: a sequence value is assigned at insert time, not commit
time. A transaction that drew 10 can commit after one that drew 11, and a
client that had already advanced its cursor to 11 would miss 10 forever.
The counter row lock makes commit order equal `change_seq` order. A
transaction holding the lock cannot be overtaken because the next writer
blocks on the row until the first commits. The lock is held only for the
final three statements, so a multi-megabyte blob insert does not serialize
other writers. On SQLite the database-level writer lock gives the same
property for free.

The cursor is distinct from all ids. Ids are client-generated and say *what*
a row is. `change_seq` is server-assigned and says *when it became
visible*.

### 9.2 Client sync

`SELECT ... FROM change_log JOIN change_entity ... WHERE change_seq >
:cursor ORDER BY change_seq LIMIT 500`. The client applies the page and
advances its cursor to the last `change_seq` it applied. Polling is the
**required** baseline: every 5 s for viewers with a live pane, 30-60 s
otherwise.

### 9.3 Notifications (optional, PostgreSQL)

`LISTEN pychron_change`. Payload is `{"seq": n, "kinds": [...],
"ms": [...], "repos": [...]}`, under 1 KB, well below the 8000-byte limit.
A notification is only a hint to poll now. Clients never take data from
it. NOTIFY is delivered on commit, in commit order, and is dropped if the
listener is disconnected. That is why the cursor poll remains the source of
truth. On reconnect the client always polls before trusting notifications.

### 10.3 Import of full history (decision D9)

The importer brings in the **full git history** of each repo's configured
branch (`import_source.branch`, default the remote's default branch; the
`data_collection` branch, `dvc/__init__.py:38`, is imported only if
listed).

**Ordering.** Commits are processed in `git rev-list --topo-order
--reverse` order, so every commit comes after its parents. Ties keep git's
order. Each commit is diffed against its first parent.

**Commit to rows.** One git commit becomes one changeset:

| Changeset field | Source |
|---|---|
| `uuid` | UUIDv5(import namespace, repo url, commit sha). Deterministic, so re-runs are idempotent. |
| `kind` | `collection` for the collection commits below, `reference` for meta-repo commits, otherwise `import` |
| `author_user_uuid` | git author email mapped to `app_user`. Unknown authors become users named `git:<email>`. |
| `client_uuid` | the importer's client row |
| `created_utc` | git author date (the commit's own offset makes it exact UTC) |
| `message` | full commit message, verbatim |
| `import_source_uuid` | this import |

Each changed file under that commit becomes one revision (UUIDv5 of
commit sha + path) of the matching subject and kind. The legacy tag in the
message (`<ISOEVO>`, `<BLANKS>`, ..., `dvc/__init__.py:44-54`) is recorded,
but the **file suffix decides the kind** (`.intercepts` → `intercepts`,
and so on). Commits often touch several kinds, and messages are free text.
A revision is created only when the file's git blob sha differs from the
blob sha of the current imported head for that (subject, kind). The
`parent_uuid` is that head, and the head moves to the new revision (a
`head_move` with reason `commit`). Merge commits therefore add revisions
only for content that differs from what the topological walk has already
imported, and non-linear history is linearized into one chain per
(subject, kind). The true git ancestry stays in `import_provenance`
(`commit_sha`, `path`, `git_blob_sha`, author, date), one row per revision
and per changeset.

**Collection revision.** For each analysis, the commit that adds its
`<runid>.json` with a `<COLLECTION>` tag, together with the following
`<ISOEVO> default collection fits`, `<BLANKS> preceding ...` and
`<ICFactor> default` commits that first add its `.intercepts`,
`.baselines`, `.blanks` and `.icfactors` (`dvc_persister.py:363-407`), is
folded into one `collection` changeset. Its author and time come from the
`<COLLECTION>` commit, and all four commit shas are kept in
`import_provenance`. The first revision of each kind is the root
(parent NULL), so rollback-to-collection behaves as in legacy
(`dvc.py:731-745`). Analyses that entered a repo without a collection
commit (`IMPORT`, `MASS SPEC REDUCED`, transfers via `dvc.py:637`) get a
collection changeset synthesized from their first commit, marked
`synthetic_collection` in provenance.

**Meta repo.** Each commit touching reference files becomes a `reference`
changeset. A level file (`<irrad>/<level>.json`) holds all positions, so it
is diffed per position, and only positions whose JSON changed get a new
`flux_position` revision. Each sensitivity list entry becomes its own
revision in list order (D5).

**Tags.** A git tag on commit C becomes a `bookmark` whose entries are the
imported heads, as of C, of every analysis in the repo.

**Volume and performance.** This must handle a decade of history (for
scale, tens of thousands of commits and hundreds of thousands of file
versions per large repo):

- Read objects through `git cat-file --batch` or libgit2, with no checkout
  per commit. Parse each distinct blob sha once (LRU keyed by blob sha):
  most commits touch a few files, and identical blobs recur.
- Write in batches of about 500 commits per transaction. Use PostgreSQL
  `COPY` for revision and payload rows and one `change_log` entry per
  batch, not per commit, so live viewers are not flooded.
- Resume: `import_source.progress_commit_sha` is updated in the same
  transaction as each batch. With deterministic ids, a crashed import
  restarts from the last committed batch with no duplicates.
- Payload rows exist only for changed files. A rough estimate for 50k
  analyses is about 6 revisions per analysis, 300k revisions and a few
  million payload rows, which PostgreSQL handles comfortably. Raw signal
  blobs dominate bytes and are content-deduplicated.
- On completion, the importer fills `published_file` and `publish_state`
  for each repo with what is already there, so the first publish run does
  not rewrite history.
- Imports run as the admin role, outside acquisition. A full-history import
  of a large repo is an offline migration step, measured on the fixture
  (action item 3).

Catalog rows come from the legacy MySQL database (catalog authority).
Values come from project repos. Reference data comes from the meta repo.
These are three `import_source` kinds.

Re-import of a repo that the publisher writes: if a file's sha equals
`published_file.file_sha256`, nothing happens. If it differs, the result is
a `hand_edit` conflict. It is resolved by an admin accepting it as a
revision (author = git author) or rejecting it. It is never silently
authoritative (ADR-0002 section 4.3).

### 10.4 Byte-comparability rules (publisher)

- JSON is written as `json.dump(obj, indent=4, sort_keys=True)`
  (`dvc/__init__.py:96-103`). `extra` columns are merged back before
  serialization.
- Timestamps are formatted in the import's `lab_time_zone` as naive ISO
  strings, as legacy wrote them (`dvc_persister.py:308-310`, `:797`).
- Paths: imported analyses reuse the path recorded in `import_provenance`.
  New analyses follow `publish_target.layout`. Legacy default is UUID names
  with `force_sublen=2` (`dvc_persister.py:975-987`, `dvc/__init__.py:178-240`).
- Spectrometer files go at the repo root as `<legacy_sha1>.json`.

### 11.3 SQLite subset and dialect differences

| Use | Tables |
|---|---|
| Acquisition outbox | `outbox_item`, `outbox_dep`, `outbox_blob`, `lease_cache`, `local_allocation`, `catalog_cache`, `outbox_meta`, `schema_version`. These are not the shared schema. |
| Offline export | The full shared schema except `ingest_receipt`, `aliquot_lease`, `publish_*`, `import_*`, plus the outbox tables (offline edits, section 8.7) |
| Test engine | The full shared schema |

Mechanical type mapping (SQLite tables are `STRICT`, so SQLite 3.37 or
later is required):

| PostgreSQL | SQLite | Note |
|---|---|---|
| `uuid` | `TEXT` + `CHECK(length(x)=36)` | Lowercase canonical form, produced only by the access layer |
| `timestamptz` | `TEXT` + `CHECK(x LIKE '____-__-__T__:__:__%Z')` | Microsecond ISO-8601 UTC |
| `bytea` | `BLOB` | |
| `jsonb` | `TEXT` + `CHECK(json_valid(x))` | JSON1 is built in |
| `double precision` / `int` / `bigint` / `boolean` | `REAL` / `INTEGER` / `INTEGER` / `INTEGER CHECK (x IN (0,1))` | |
| `GENERATED ALWAYS AS ... STORED` | same syntax | 3.31 or later |

Behavioral differences the access layer owns:

| Concern | PostgreSQL | SQLite |
|---|---|---|
| Row lock for reservation | `SELECT ... FOR UPDATE` | `BEGIN IMMEDIATE` (database lock) |
| Change notification | `LISTEN`/`NOTIFY` | none; poll only |
| Immutability triggers | plpgsql function + trigger | `CREATE TRIGGER ... BEGIN SELECT RAISE(ABORT,'append-only'); END` |
| Blob hash CHECK | `sha256()` in a CHECK | not available; verified by the access layer on write and by `elctl db verify` |
| FK enforcement | always | `PRAGMA foreign_keys=ON` on every connection (asserted at open) |
| Upsert, `RETURNING` | yes | yes (3.24 / 3.35 or later) |
| Deferred FKs (forward refs across tables) | `ALTER TABLE ADD FOREIGN KEY` | inline `REFERENCES ... DEFERRABLE INITIALLY DEFERRED`; table order is chosen so only `ref_object` scopes and `load.holder_ref_revision_uuid` need it |
| Error classes | SQLSTATE | extended result codes. Both are mapped to `retryable`/`permanent`/`conflict` in one table in `src/sql/errors.cpp` |

The SQLite DDL is generated from the PostgreSQL migration by a checked-in
tool (`tools/ddl_sqlite.py`) and committed. A CI test introspects both
engines (`information_schema` / `pragma_table_info`) and fails if the table,
column, PK, UNIQUE or FK sets differ, apart from the documented exclusions.

### 11.4 Schema versioning and evolution

- Migrations are numbered `NNNN_<name>.sql` per dialect, forward-only. Each
  is recorded in `schema_version` with a checksum. A checksum mismatch on
  startup is a fatal `Config` error.
- Changes within a major version are **additive only**: new tables, new
  nullable columns, new CHECK values, new indexes. Renames and drops require
  a major bump, an expand/contract sequence across two releases, and a
  publisher layout version bump if the file shape changes.
- `schema_compat` holds `min_writer_version` and `min_reader_version`.
  Clients older than `min_writer_version` open read-only and say so.
- Outbox payloads carry `payload_schema_version`. The server ingest code
  accepts the current version and the previous one, so acquisition PCs can
  be upgraded after the server. Anything else goes to `poison` with
  `unsupported payload version`, never silent loss.
- Payload tables are never altered in place for old revisions. New fields
  are nullable columns or keys in `extra`.

### 12.2 Interfaces

```cpp
namespace pychron::persistence {

enum class Kind { Signals, Intercepts, Baselines, Blanks, IcFactors, Tags,
                  Annotation, RefPins, Identity, Cosmogenic, InterpretedAge, RefValue };

struct Actor { Uuid user; Uuid client; };                 // stamped on every changeset

struct Conflict {
  Uuid subject; Kind kind;
  std::optional<Uuid> expected, actual;
  ChangesetInfo actual_by;                                // author, client, created_utc, message
};
struct Committed { Uuid changeset; ChangeSeq seq; };
// A lost CAS race is an expected outcome, not an Error.
using CommitOutcome = std::variant<Committed, std::vector<Conflict>>;

class IUnitOfWork {
 public:
  virtual ~IUnitOfWork() = default;
  // Stages a revision; parent = expected head. Returns the client-generated id.
  virtual Uuid add_revision(Uuid subject, Kind, RevisionPayload, std::optional<Uuid> expected_head) = 0;
  virtual void move_head(Uuid subject, Kind, std::optional<Uuid> expected, Uuid to, MoveReason) = 0;
  virtual Result<CommitOutcome> commit(ChangesetKind, std::string message) = 0;  // one transaction
};

class IStore {
 public:
  virtual ~IStore() = default;
  virtual Result<std::unique_ptr<IUnitOfWork>> begin(const Actor&) = 0;
  virtual Result<std::optional<AnalysisView>> load_analysis(Uuid, const LoadOptions&) = 0;  // heads|bookmark
  virtual Result<std::vector<AnalysisSummary>> find_analyses(const AnalysisQuery&) = 0;
  virtual Result<std::vector<RevisionInfo>> history(Uuid subject, Kind) = 0;
  virtual Result<RefResolution> resolve_refs(Uuid analysis, const RefPolicy&) = 0;
  virtual Result<ChangePage> changes_since(ChangeSeq cursor, int limit) = 0;
  virtual Result<IngestAck> ingest(const IngestItem&) = 0;   // idempotent; used by Uploader
  virtual Result<std::vector<int>> reserve_aliquots(const Actor&, Uuid identifier, int n, Uuid queue) = 0;
};

Result<std::unique_ptr<IStore>> open_store(const StoreConfig&);  // "postgresql://..." | "sqlite:..."
}
```

Errors use the core `Result<T>` and `Error`. Infrastructure failures map to
the existing `ErrorKind` values: `NotConnected` (server unreachable),
`Timeout`, `Io` (disk, SQLite), `Protocol` (constraint or version
mismatch), `Config` (migration checksum, unsupported schema). No new
`ErrorKind` is needed. CAS conflicts are values, and "not found" is an
empty `optional`. Driver exceptions (libpqxx) are caught inside `src/pg/`
and never cross the library boundary.

### 12.3 Unit of work

A unit of work stages in memory. `commit()` opens one transaction, applies
section 5.4's order (payload inserts, ordered CAS, `head_move`, cursor) and
closes it, so transactions stay short and callers cannot get the order
wrong. Destruction without commit discards the staging. A unit of work is
single-threaded and never shared across Scheduler tasks.

#### 12.4.1 Amendment 2026-10-02: TinyORM (owner decision)

The owner chose **TinyORM** (v0.38.1, query builder and ORM, no `tom` CLI)
over option A. TinyORM runs on QtSql (`QSQLITE`, `QPSQL`), so this amends
the "Qt SQL is excluded" rule for this one library, with these constraints:

- Qt stays behind the library boundary. `Qt6::Core`, `Qt6::Sql` and
  TinyORM are PRIVATE dependencies of `pychron::persistence`. Public headers
  under `include/pychron/persistence/` use only the standard library and
  core types, so no consumer sees Qt. QtCore/QtSql need no GUI, so `elctl`
  stays headless.
- `src/pg/` and `src/sqlite/` become one `src/tiny/` backend. Driver
  exceptions (`Orm::Exceptions::SqlError`) are caught there; SQLSTATE and
  SQLite result codes are mapped in `src/sql/errors.cpp` as before.
- The SQL-first design is unchanged. The schema is still the hand-written
  PostgreSQL migration plus the generated SQLite DDL (section 11.3). The
  compare-and-swap, the change-cursor statements and engine introspection
  stay explicit SQL in `src/sql/statements.hpp`. Simple inserts use the
  TinyORM query builder. TinyORM models (`Orm::Tiny::Model`) are not used:
  they need a single-column primary key, and most tables here have
  composite keys.
- Transactions are opened with explicit `BEGIN IMMEDIATE` (SQLite) and
  `BEGIN` (PostgreSQL). TinyORM's `beginTransaction()` issues a deferred
  `BEGIN` on SQLite, which deadlocks under concurrent writers.
- QtSql returns PostgreSQL `timestamptz` as `QDateTime`, which keeps only
  milliseconds. Timestamps are therefore read back as text through
  `to_char(... 'US')` so the microsecond UTC values (P4) survive.
- `LISTEN`/`NOTIFY` (section 9.3) will use
  `QSqlDriver::subscribeToNotification` when D6 lands. `pg_notify` is
  already sent on every write.
- Platforms: the library is built when `find_package(Qt6 COMPONENTS Core
  Sql)` succeeds (`PYCHRON_PERSISTENCE`, default ON). It is skipped, with a
  warning, elsewhere. CI builds it on Linux (apt Qt 6.4 SQL drivers), macOS
  (Homebrew Qt, UI job) and against a `postgres:16` service. Windows CI has
  no Qt yet and skips it.
- vcpkg: TinyORM and range-v3 are fetched from git at pinned release
  commits (FetchContent with `FIND_PACKAGE_ARGS`, so a vcpkg `tinyorm` port
  is used when present). Action item 9 is superseded.

### 12.7 Security and operations

- **Roles** as in section 11.2. One login per client machine, mapped to its
  role, with credentials in the OS keychain (macOS) or Credential Manager
  (Windows), never in TOML. The person is recorded as `author_user_uuid`.
  It is asserted by the application, not authenticated by the database
  (decision D7). Every changeset and `change_log` row carries both the
  client and the user.
- **TLS** is required: `sslmode=verify-full`, with the lab CA distributed
  with the client config. A server on the acquisition PC still uses TLS
  for remote clients and may allow local socket connections.
- **Server backup**: continuous WAL archiving plus a nightly base backup
  (point-in-time recovery), and a weekly logical dump restored into a
  scratch instance by `elctl db verify --restore-test`. The git mirror is an
  additional, partial off-site copy, not the backup.
- **Outbox backup**: until an item is acked, the outbox holds the only copy.
  It lives on a local disk (not a network share), with `synchronous=FULL`.
  An hourly `VACUUM INTO` snapshot goes to a second disk or share. The
  status alarm fires when the oldest pending item exceeds 30 min.
- **Clocks**: client timestamps (`timestamp_utc`, `created_utc`) need NTP.
  Ordering and sync never rely on them, only on `change_seq`.

### 13.2 Decisions (owner, 2026-10-01)

The nine review questions, numbered as asked (D1-D9).

1. **D1 Provisional renumbering: accepted.** A run added during an outage
   runs with a provisional aliquot (`*`) and is renumbered at ingest only on
   collision, recorded as an `identity` revision plus `sync_conflict`
   (section 8.5).
2. **D2 Aliquot gaps: accepted** from released leases and cancelled runs.
3. **D3 Offline export accepts edits.** Edits are local changesets plus
   `changeset` outbox items, uploaded later with CAS. Conflicts produce a
   `sync_conflict` report and a re-apply or discard choice (section 8.7).
4. **D4 No lab-manager role and no approval step for reference data.** Any
   authenticated writer may publish a new reference revision. It is still
   revisioned, audited and reversible (section 6.2). This closes the ADR's
   "revisit later" item on review.
5. **D5 Sensitivity and gains use legacy "latest"** (head). There is no
   valid-time axis. Analyses still pin or fingerprint the revision used
   (sections 4.3, 6.2).
6. **D6 Catalog edits are audited by the change log alone**
   (`change_entity.detail` field diff), not revisioned.
7. **D7 App-asserted identity.** There are no per-person database logins.
   Client and user ids go on every changeset and `change_log` row. Client
   database roles are acquisition writer, reduction writer and viewer;
   publisher and admin are service roles (section 11.2).
8. **D8 Fixture:** `github.com/NMGRLData/MetaData` is the importer and
   publisher proof fixture for reference data.
9. **D9 Full git history is imported** as revision chains (section 10.3).
